# HTML 시안 뽑기 → 선택 → 반영

디자인 요청이 오면 바로 코드나 Figma를 만들지 않는다. 먼저 **방향이 서로 다른 HTML 시안 여러 개**를 만들어 한 화면에서 비교하게 하고, 사용자가 고른 것만 실제 대상에 반영한다.

이렇게 하는 이유: 코드·Figma 반영은 비싸고 되돌리기 번거롭다. HTML 시안은 싸고 빠르며, 사용자는 말로 설명된 계획보다 눈에 보이는 결과물을 보고 훨씬 정확하게 고른다. 시안 비교 자체가 "확인받고 진행"하는 단계 역할을 한다.

## 전체 흐름

1. 요청 파악 (모호할 때만 짧게 질문)
2. 맥락 수집 (프로젝트 / Figma의 기존 디자인 언어)
3. 5가지 방향 정하기
4. 시안 HTML 작성 + 비교 페이지 생성 + 브라우저로 열기
5. 사용자 선택 (또는 수정·재시안)
6. 선택한 시안을 코드 또는 Figma에 반영

---

## 1. 요청 파악

요청이 충분히 구체적이면 질문 없이 바로 시안을 만든다. 시안 자체가 질문 역할을 하므로, 애매한 디테일은 시안마다 다르게 풀어보면 된다.

다음처럼 **핵심이 비어 있어 시안 방향을 정할 수 없을 때만** AskUserQuestion으로 1~2개만 묻는다.
- 무엇을 디자인하는지 불분명 (어떤 화면/컴포넌트인지)
- 반영 대상이 결과물 형태를 크게 바꾸는데 알 수 없음 (예: 모바일 앱인지 데스크톱 웹인지)
- 꼭 들어가야 할 콘텐츠/기능을 추측할 근거가 전혀 없음

시안 개수는 사용자가 따로 말하지 않으면 **5개**. "3개만", "10개" 등 말하면 그대로 따른다.

반영 대상(코드 / Figma)은 이 시점에 몰라도 된다. 요청 문맥("피그마에", 현재 프로젝트 코드 등)으로 추정해 두고, 6단계에서 불분명하면 그때 묻는다.

## 2. 맥락 수집

시안이 실제로 쓰일 곳의 디자인 언어를 따라야 고른 뒤 반영이 자연스럽다. 시간을 많이 쓰지 말고 핵심만 빠르게 본다.

- **코드 프로젝트 안이라면**: 디자인 토큰(tailwind config, CSS 변수, theme 파일), 폰트, 주요 공통 컴포넌트(Button, Input, Card, Header 등), 비슷한 기존 화면 1~2개를 훑는다. 색·폰트·라운드·간격 스케일을 시안에 그대로 쓴다.
- **Figma 반영이라면**: designagent 도구(`get_design_md`, `list_variables_and_styles`, `list_page_nodes`, `take_screenshot`)로 색·폰트·화면 크기·공통 컴포넌트를 파악한다. 메모리에 해당 파일의 컨벤션이 있으면 그걸 우선한다.
- **아무 맥락이 없으면**: 자유롭게 하되, 시안 간 차이가 "디자인 방향"에서 나오도록 한다.

기존 디자인 시스템이 있으면 5개 시안 모두 그 시스템 안에서 방향만 달리한다 (레이아웃·정보 구조·강조점이 다르고, 브랜드 색/폰트는 공유). 시스템이 없을 때만 톤·색까지 과감하게 다르게 가져간다.

## 3. 5가지 방향 정하기

HTML을 쓰기 전에 각 시안의 방향을 한 줄씩 먼저 정한다. 이걸 건너뛰면 5개가 비슷비슷해지기 쉽다.

방향이 **확연히** 달라야 한다. 색만 바꾼 변주는 하나의 시안으로 친다. 차이를 낼 축의 예:
- 레이아웃 구조: 단일 컬럼 / 2단 분할 / 카드 그리드 / 리스트 / 사이드바+콘텐츠 / 풀블리드 히어로
- 정보 우선순위: 무엇을 가장 먼저, 가장 크게 보여주는가
- 밀도: 여백 많은 미니멀 / 정보 밀도 높은 실무형
- 인터랙션 방식: 한 페이지에 다 / 탭 / 스텝 / 아코디언
- 톤: 차분·중립 / 강한 대비·볼드 / 친근·라운드

각 방향에는 짧은 이름(예: "카드 그리드형", "스텝 진행형")과 한 줄 설명(무엇을 우선시했고 어떤 상황에 맞는지)을 붙인다. 이것이 비교 페이지 탭에 그대로 표시된다.

## 4. 시안 작성

### 저장 위치

임시 폴더에 저장한다. 세션 scratchpad 디렉터리가 시스템 프롬프트에 있으면 그 아래, 없으면 `/tmp` 아래에 둔다.

```
<scratchpad 또는 /tmp>/design-drafts/<주제-slug>/
├── drafts.json   ← 비교 페이지 정보
├── A.html
├── B.html
├── ...
└── index.html    ← 스크립트가 생성
```

### 시안 HTML 작성 원칙

- **파일 하나로 완결**: CSS는 `<style>`에 인라인. 외부 리소스는 CDN 폰트(예: Pretendard `https://cdn.jsdelivr.net/gh/orioncactus/pretendard/dist/web/variable/pretendardvariable.css`), 아이콘이 필요하면 인라인 SVG 정도만. 빌드 과정 없이 파일을 열면 바로 보여야 한다.
- **실제 같은 콘텐츠**: lorem ipsum 대신 그 서비스에 실제로 들어갈 법한 한국어 문구·숫자·이름을 쓴다. 사용자는 실제 콘텐츠가 들어갔을 때의 느낌으로 판단한다.
- **반영 대상의 크기에 맞춤**: 데스크톱 웹은 보통 1440(또는 프로젝트/Figma 규격, 예: 1920), 모바일은 390. `drafts.json`의 `width`에 이 값을 적는다. 반응형까지 만들 필요는 없다.
- **요청한 것만**: 요청에 없는 부가 요소(통계 배지, 장식용 요소, 과한 섹션)를 끼워넣지 않는다. 방향 차이는 구조와 우선순위로 낸다.
- **반영을 염두에 둔 구조**: 시맨틱 태그, 의미 있는 class 이름, CSS 변수로 색·간격 정의. 6단계에서 코드나 Figma로 옮기기 쉬워진다.
- 상태가 중요한 화면(폼 에러, 빈 상태 등)은 요청에 그 상태가 포함될 때만 표현한다.

### drafts.json

```json
{
  "title": "로그인 페이지",
  "request": "사용자의 원래 요청 한 줄",
  "width": 1440,
  "drafts": [
    { "id": "A", "file": "A.html", "name": "중앙 카드형", "summary": "가장 익숙한 구조. 폼에만 집중하게 함" },
    { "id": "B", "file": "B.html", "name": "좌우 분할형", "summary": "왼쪽 브랜드 비주얼 + 오른쪽 폼. 첫인상 강조" }
  ]
}
```

시안마다 폭이 다르면 해당 항목에 `"width"`를 따로 넣을 수 있다.

### 비교 페이지 생성 & 열기

```bash
python3 <이 스킬 경로>/scripts/build_index.py <시안 폴더>
open <시안 폴더>/index.html
```

비교 페이지는 상단 탭으로 시안을 전환하고(키보드 1~9, ←/→), 화면 맞춤/실제 크기 보기를 토글하며, 각 시안을 새 탭에서 따로 열 수 있다.

열고 나면 사용자에게 짧게 알린다: 각 시안 이름과 한 줄 특징, 그리고 "마음에 드는 걸 골라주세요. 섞거나(예: B 레이아웃 + D 톤) 수정해도 됩니다."

## 5. 선택 · 수정 · 재시안

사용자의 반응에 따라:
- **하나를 고름** → 6단계로.
- **조합/수정 요청** ("B인데 헤더는 A처럼", "C에서 버튼 더 크게") → 해당 시안을 수정하거나 조합한 새 시안을 만들어 같은 폴더에 추가(`F.html` 등), `drafts.json` 갱신 후 스크립트를 다시 돌리고 새로고침을 안내한다. 확정될 때까지 반복.
- **다 별로** → 무엇이 별로인지 한 번 묻거나, 피드백이 있으면 그걸 반영해 새 방향으로 다시 뽑는다. 새 라운드는 `<주제-slug>-r2/` 폴더로 만든다.
- **특정 시안 변주 요청** ("B 느낌으로 3개 더") → 그 시안을 기준으로 변주 시안을 새 라운드로 뽑는다.

## 6. 선택한 시안 반영

반영 대상이 불분명하면 여기서 묻는다 (코드 / Figma / 둘 다, 그리고 어느 파일·페이지에).

### 코드에 반영

시안 HTML을 그대로 붙여넣지 않는다. 시안은 "어떻게 생겨야 하는지"의 기준이고, 구현은 프로젝트의 방식으로 한다.
- 프로젝트의 프레임워크·스타일링 방식(Tailwind, CSS Modules, styled-components 등)과 기존 공통 컴포넌트를 사용한다. 이미 있는 Button/Input을 다시 만들지 않는다.
- 하드코딩 색·간격 대신 프로젝트 토큰을 쓴다. 시안의 값이 토큰과 살짝 다르면 토큰 쪽에 맞춘다.
- 시안의 더미 콘텐츠는 실제 데이터/props/i18n 구조에 맞게 바꾼다.
- 반영 후 가능하면 실행해서 시안과 비교 확인한다.

### Figma에 반영

designagent 도구를 사용한다.
- 공통 컴포넌트가 있으면 `instantiate_component`/`clone`으로 재사용하는 것을 우선하고, 나머지 구조는 `html_to_design`으로 시안 HTML을 옮긴 뒤 다듬는다.
- `html_to_design`은 웹폰트를 대체 폰트로 바꿀 수 있으니, 결과의 폰트를 확인하고 필요하면 기존 텍스트 노드를 복제하거나 `set_text_style`로 맞춘다.
- 반영 후 `take_screenshot`으로 시안과 비교해 어긋난 부분을 고친다.
- 브리지로 안 되는 작업(섹션/페이지 생성, variant 등)은 사용자에게 직접 하도록 안내한다.

반영이 끝나면 무엇을 어디에 만들었는지 짧게 보고한다. 시안 폴더는 임시라서 정리할 필요 없다.
