# 좋은 코드(변경하기 쉬운 코드) 검토 & 리팩터링 스킬

프론트엔드 코드가 **"변경하기 쉬운 코드"** 인지 토스 [Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/) 기준으로 검토하고, 문제를 발견하면 코드까지 직접 리팩터링한다.

핵심 전제: **좋은 코드 = 변경하기 쉬운 코드.** 이를 네 가지 기준으로 판단한다.

1. **가독성 (Readability)** — 코드를 읽는 사람의 인지 부하가 낮은가
2. **예측 가능성 (Predictability)** — 이름·파라미터·반환값만 보고 동작을 예측할 수 있는가
3. **응집도 (Cohesion)** — 함께 바뀌는 코드가 함께 있는가
4. **결합도 (Coupling)** — 코드를 바꿀 때 영향이 미치는 범위가 좁은가

## 언제 이 스킬을 쓰나

사용자가 다음을 요청할 때:
- 코드 품질·가독성·구조·유지보수성 검토·개선·리팩터링
- "코드 품질 봐줘", "가독성 개선", "좋은 코드인지 검토", "리팩터링 관점에서 봐줘", "이 함수/컴포넌트 정리해줘" 등

## 작업 흐름

1. **대상 파악** — 사용자가 지정한 파일/디렉터리/컴포넌트/함수를 읽는다. 지정이 없으면 범위를 물어본다. JSX/TSX, Vue, Svelte, 순수 TS/JS 모두 대상.
2. **검토** — 아래 4대 기준 체크리스트로 코드를 훑는다. 각 발견 항목을 어떤 기준을 위반했는지와 함께 표시한다.
3. **문제 정리** — `파일:라인` + 위반 기준(가독성/예측/응집/결합) + 이유 + 개선 방향으로 요약해 사용자에게 보여준다. 심각도(치명적/권장/취향)로 묶으면 좋다.
4. **리팩터링** — 명백한 개선은 바로 Edit로 고친다. 트레이드오프가 갈리는 항목(특히 결합도 vs 중복, 추상화 수준)은 아래 "충돌 해소 원칙"에 따라 판단하고, 판단이 애매하면 사용자 의도를 먼저 확인한다.
5. **검증** — 동작이 바뀌지 않았는지 확인한다. 프로젝트에 테스트가 있으면 돌리고, 타입체크·lint가 있으면 실행한다. 없으면 리팩터링이 순수 구조 변경임을 설명한다.

> ⚠️ **가장 중요한 원칙: 네 기준은 서로 충돌한다.** 하나를 좋게 하면 다른 하나가 나빠질 수 있다(예: 중복 제거 → 결합도 증가, 추상화 → 가독성 저하). 무조건 규칙을 적용하지 말고, **"이 코드가 앞으로 어떻게 바뀔 것 같은가"** 를 기준으로 우선순위를 정한다. 아래 "충돌 해소 원칙" 참고.

## 검토 체크리스트

### 📖 1. 가독성 (Readability) — 인지 부하를 낮춘다

- [ ] **함께 실행되지 않는 코드 분리** — 한 컴포넌트/함수 안에 조건에 따라 갈리는 두 흐름(예: `isViewer ? ... : ...`)이 뒤섞여 있으면, 각 분기를 별도 컴포넌트/함수로 분리한다.
  - `SubmitButton` 하나에 viewer용·admin용 로직이 섞임 → `ViewerSubmitButton` / `AdminSubmitButton` 으로 분리.
- [ ] **구현 세부사항 추상화** — 컴포넌트의 핵심 역할을 읽는 데 방해되는 세부 로직(확인 다이얼로그, 복잡한 핸들러 등)은 전용 컴포넌트/훅으로 감싼다. 읽는 사람이 한 번에 고려할 맥락의 수를 줄인다.
- [ ] **로직 종류에 따라 함수·훅 분리** — 하나의 훅/함수가 여러 종류의 책임(쿼리 파라미터 + 상태 + API)을 다루면 종류별로 쪼갠다. 관련 없는 값 변경에 따른 불필요한 리렌더/사이드이펙트를 막는다.
  - 모든 쿼리 파라미터를 관리하는 `usePageState()` → `useCardIdQueryParam()` 처럼 파라미터별 훅으로.
- [ ] **복잡한 조건에 이름 붙이기** — 여러 연산자가 얽힌 조건은 의미를 담은 변수로 추출한다.
  - `const isSameCategory = category.id === target.id;` / `const isPriceInRange = ...` 뒤에 `filter(x => isSameCategory && isPriceInRange)`.
  - 단, **단순·일회성 조건(`arr.map(x => x*2)` 등)은 오히려 이름을 붙이지 않는다.** 이름 붙이는 기준: 복잡하거나, 재사용되거나, 단위 테스트가 필요할 때.
- [ ] **매직 넘버에 이름 붙이기** — 맥락 없는 숫자 리터럴(`300`, `86400` 등)은 명명 상수로. `const ANIMATION_DELAY_MS = 300;`
- [ ] **시점 이동(point-of-view shift) 줄이기** — 하나의 로직을 이해하려고 `policy.canInvite → getPolicyByRole() → POLICY_SET` 처럼 파일·함수를 계속 오가야 하면, `switch` 로 조건을 펼치거나 정책 매핑을 컴포넌트 안 객체로 인라인해 위→아래로 읽히게 한다.
- [ ] **삼항 연산자 단순화** — 중첩 삼항은 즉시실행함수 + 순차 `if` 로 바꿔 각 조건과 결과를 명확히 한다.
  ```ts
  const status = (() => {
    if (A && B) return "BOTH";
    if (A) return "A";
    if (B) return "B";
    return "NONE";
  })();
  ```

### 🔮 2. 예측 가능성 (Predictability) — 이름만 보고 동작을 안다

- [ ] **겹치지 않는 이름 쓰기** — 라이브러리를 감싸면서 원래와 같은 이름(`http`)에 인증 같은 추가 동작을 몰래 넣지 않는다. `http.get()` 은 순수 HTTP를 기대하게 되므로, 래퍼는 `httpService.getWithAuth()` 처럼 동작이 드러나는 이름으로.
- [ ] **같은 종류 함수의 반환 타입 통일** — 비슷한 부류의 함수/훅은 반환 형태를 일치시킨다. API 훅은 일관되게 Query 객체를, 검증 함수는 `{ ok: boolean; reason?: string }` 처럼 통일. 하나는 data만, 하나는 Query를 반환하는 식의 불일치를 없앤다.
- [ ] **숨은 로직 드러내기** — 이름·파라미터·반환값으로 예측할 수 없는 사이드이펙트(예: `fetchBalance()` 안의 로깅)를 함수에 숨기지 않는다. `fetchBalance()` 는 잔액 조회만 하고, 로깅은 호출부에서 명시적으로.

### 🧲 3. 응집도 (Cohesion) — 함께 바뀌는 것을 함께 둔다

- [ ] **함께 수정되는 파일을 같은 디렉터리에** — 타입별(components/, hooks/, utils/) 대신 도메인/기능별 폴더 구조를 쓴다. 각 도메인이 자기 components·hooks·utils 를 가지면, 도메인 간 import 가 곧바로 눈에 띄고, 기능 제거 시 폴더 하나만 지우면 된다.
- [ ] **매직 넘버로 인한 동기화 깨짐 방지** — 애니메이션 시간과 그에 맞춘 delay 처럼 함께 바뀌어야 하는 값은 같은 상수(`ANIMATION_DELAY_MS`)를 공유해, 한쪽만 바뀌어 조용히 깨지는 일을 막는다. (가독성 항목과 연결되지만 여기선 "동기화" 관점.)
- [ ] **폼(form) 응집도 결정** — 폼 검증을 필드 단위로 둘지 폼 전체 단위로 둘지 선택한다. 기준은 **"무엇이 함께 바뀌는가".**
  - **필드 단위**: 각 필드가 독립적·전문적 검증(비동기 중복확인, 포맷 검증)을 갖거나, 필드가 여러 폼에서 재사용될 때.
  - **폼 단위(스키마)**: 모든 필드가 하나의 업무(결제, 배송정보)를 이루거나, 다단계 위저드에서 이전 입력이 다음에 영향을 주거나, 필드끼리 서로 참조(비밀번호 확인, 합계 계산)할 때.

### 🔗 4. 결합도 (Coupling) — 변경의 영향 범위를 좁힌다

- [ ] **책임을 하나씩** — 하나의 훅/함수가 여러 파라미터·책임을 한꺼번에 쥐고 있으면(`usePageState()` 가 모든 쿼리 파라미터 관리) 파라미터별로 분리해 변경 영향 범위를 좁힌다. (가독성의 "로직 종류 분리"와 같은 리팩터링을 결합도 관점에서 본 것.)
- [ ] **성급한 공통화보다 중복 허용** — 여러 페이지가 공유하는 훅/컴포넌트가, 페이지마다 동작(로깅·UI·분기)이 달라질 여지가 있다면 **공통화하지 말고 중복을 허용**한다. 지금 같은 코드라는 이유로 묶으면, 요구사항이 갈릴 때 공통 코드가 분기·플래그로 오염된다. **동작·로깅·모양이 앞으로도 계속 동일할 때만** 공통화한다.
- [ ] **Props Drilling 제거** — 중간 컴포넌트가 자기가 안 쓰는 props 를 그냥 아래로 전달하고만 있으면 결합도가 높다(이름 하나 바꾸면 여러 컴포넌트 수정). 해결:
  1. **먼저 Composition(합성)** — `children` 으로 컴포넌트를 넘겨 중간 전달 계층을 없앤다.
  2. **그래도 깊으면 Context API** — 진짜 깊은 트리에만. Context 를 남발하지 말고 합성을 먼저 소진한다. 명시적 props 는 의존성을 문서화한다는 점을 기억.

## 충돌 해소 원칙 (트레이드오프 판단)

네 기준이 부딪칠 때 규칙을 기계적으로 적용하지 말고 아래로 판단한다.

- **중복 제거 ↔ 결합도**: 중복을 없애면 결합도가 올라간다. **"이 코드들이 앞으로 서로 다르게 바뀔 가능성"** 이 있으면 중복을 허용한다. 항상 똑같이 바뀔 것이 확실할 때만 공통화.
- **추상화 ↔ 가독성**: 추상화는 세부를 숨겨 가독성을 높이지만, 과하면 오히려 시점 이동을 늘려 가독성을 해친다. 추상화 계층을 넘나들며 읽어야 이해되는 코드라면 인라인이 낫다.
- **한 파일에 모으기(응집) ↔ 파일 분리(가독)**: 함께 바뀌는 것은 모으되, 한 파일/함수가 여러 종류의 책임으로 비대해지면 종류별로 나눈다.
- **판단 기준은 항상 "변경 용이성"**: 어느 쪽이 이 코드의 미래 수정 비용을 낮추는가로 결정한다. 애매하면 사용자에게 이 코드가 앞으로 어떻게 바뀔지 물어본 뒤 정한다.

## 리팩터링 시 지킬 것

- **동작을 바꾸지 않는다.** 순수 구조 개선이 원칙. 버그를 발견하면 리팩터링과 분리해 따로 보고한다.
- **한 번에 하나의 기준씩** 적용하고, 각 변경이 왜 개선인지(어떤 기준을 좋게 하는지) 짧게 설명한다.
- 사용자 코드베이스의 기존 컨벤션(네이밍, 폴더 구조, 상태관리 라이브러리)을 따른다. 이 스킬의 예시 형태를 강요하지 않는다.
- 규칙 준수 자체가 목적이 아니다. **읽는 사람과 미래의 수정이 더 쉬워지는가**가 유일한 기준이다.
